# PLC 기반 자동 조리 공정 제어

> **쉽게 말하면**
> 
> 버튼 하나로 라면 물을 재고 끓이고 면을 넣는 순서를 기계가 알아서 하도록 만든 실습입니다. 물의 양을 재는 저울이 값을 못 읽어서 다음 단계로 안 넘어갔습니다. 이미 다 조립해 놓은 상태라 아무 데나 뜯어볼 수 없었기 때문에, 되돌리기 쉬운 것부터 — 프로그램 → 실제 입력값 → 배선 → 센서 순서로 하나씩 지워가며 저울 자체가 고장 났다는 걸 확정했습니다.

## 문제

MITSUBISHI PLC 기반 자동 조리 공정을 통합 테스트하던 중, 물 계량 공정의 로드셀이 무게를
정상 측정하지 못했다. 라면 물의 양을 재는 센서였고, 기준값 판정이 이뤄지지 않아
**다음 공정으로 시퀀스가 전환되지 않았다.**

증상이 나온 시점이 문제를 어렵게 만들었다. **배선을 모두 연결하고 시스템을 다 조립한
뒤였다.** 원인 후보는 배선 불량, 프로그램 오류, 센서 고장 셋이었는데, 뒤쪽 후보를
확인하려면 조립을 되돌려야 했다.

## 검토와 판단

셋 다 가능성이 있을 때는 **되돌리기 쉬운 것부터, 확인 비용이 싼 것부터** 지우는 게 맞다고
봤다. 완성된 상태에서는 이 순서가 특히 중요했다. 센서부터 뜯었다가 배선 문제였다면
접속부를 다시 만들면서 새 변수를 들여오게 된다. 프로그램은 되돌리는 비용이 0 이므로
거기서 시작했다.

| 순서 | 확인한 것 | 결과 |
|---|---|---|
| 1 | GX Works2 에서 판정 조건 구조 점검 | 로직 오류 가능성을 낮춤 |
| 2 | 실제 입력값 모니터링 | 특정 구간에서 값이 비정상 |
| 3 | 배선 점검·재체결 | 변화 없음 |
| 4 | 센서 교체 | **로드셀 자체 결함으로 확정** |

점검은 프로그램 → 실제 입력값 → 배선 → 센서 순으로 좁혀 갔고, 마지막 단계에서
로드셀 자체 결함으로 확정했다.

## 결과

- 센서 교체 후 계량값이 안정화되고 기준값 판정이 정상화
- **물 계량 → 끓이기 → 면 투입 → 자동 이동** 전체 시퀀스 구현 및 통합 테스트 완료

## 내 기여

팀장으로 PLC 프로그램 설계, 배선 작업, 센서를 활용한 조리 로직 개발을 담당했다.
공정 간 시퀀스를 설계하고 제어 알고리즘을 적용했다.

## 다시 한다면

프로그램에서 멈추지 않고 실제 입력값과 배선, 센서까지 차례로 확인한 것이 답에 닿은 이유였다.
제어 로직이 맞아도 계량값이 틀리면 원인은 로직 밖에 있다.

지금 다시 한다면 **단계마다 관찰한 값을 남기겠다.** 같은 증상이 재발했을 때 대조할 기준이 되고,
어느 단계에서 정상이었는지가 곧 원인 범위를 좁히는 근거가 된다.

## 쉽게 정리하면

**무엇이 문제였나.** 자동으로 라면을 조리하는 공정을 만들어 통합 시험을 하던 중, 물의 무게를 재는 센서가 값을 제대로 내지 못했습니다. 무게 판정이 안 되니 다음 공정으로 넘어가지 않았습니다. 원인 후보는 배선 불량, 프로그램 오류, 센서 고장 셋이었습니다. 하필 배선을 다 연결하고 조립까지 끝낸 뒤에 나온 증상이라, 뒤쪽 후보를 확인하려면 만들어 놓은 것을 되돌려야 했습니다.

**무엇을 했나.** 되돌리기 쉬운 것부터 순서를 정해놓고 하나씩 지웠습니다. 프로그램을 보고, 실제로 들어오는 값을 지켜보고, 배선을 점검하고, 마지막에 센서를 바꿨습니다. 센서를 바꾸고 나서야 값이 안정됐고, 그래서 센서 자체의 결함으로 확정했습니다. 순서를 거꾸로 잡아 센서부터 뜯었다면, 배선을 다시 만들면서 원인이 하나 더 늘어날 수도 있었습니다.

**무엇이 달라졌나.** 물 계량부터 끓이기, 면 투입, 자동 이동까지 전체 순서를 구현해 통합 시험을 마쳤습니다. 여기서 남은 것은 결과보다 방법입니다. 프로그램이 맞아도 값이 틀리면 원인은 프로그램 밖에 있다는 것입니다.

**아직 확인되지 않은 것.** 각 단계에서 관찰한 값이 지금 남아 있지 않습니다. 그래서 같은 증상이 다시 났을 때 대조할 자료가 없습니다. 다시 한다면 단계마다 값을 남기겠습니다.
